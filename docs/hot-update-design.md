# ExcelManus 升级与部署

适用版本：1.8.0 源码 · 更新日期：2026-09-21

[文档导航](README.md) · [运维手册](ops-manual.md) · [English operations guide](ops-manual_en.md)

ExcelManus 当前有桌面应用、本机 Git 源码和服务器三种运行形态。升级会影响正在执行的任务，应在合适的时间进行。服务器部署可使用候选实例健康检查后切换的 blue/green 辅助流程；桌面和本机 Git 更新仍使用原有停机流程。

服务器滚动切换可使用 `deploy/rolling_upgrade.sh`：它先启动候选后端并轮询 `/api/v1/health`，健康检查失败时保留旧实例；只有 nginx 配置检查和 reload 成功后才终止旧 PID。通过 `EXCELMANUS_NGINX_CONF` 指向实际配置，并让新旧实例共享 `EXCELMANUS_HOME` 与工作区卷。

## 桌面应用

桌面版从应用资源启动随包前后端及代码运行时，更新方式是安装新的应用包。应用数据保留在 Electron 用户数据目录中的 `profile/`，或显式指定的 `EXCELMANUS_HOME`。

可从「设置 → 版本」或「帮助 → 检查更新」检查正式发布并下载适用的安装包。GitHub API 限流、连接超时、服务错误或返回无效 JSON 时会尝试官方发布页；API 请求限时 4 秒，发布页与资产请求共用 8 秒期限，并继续校验正式版本与资产来源。Windows 检测已有安装后，在原位置提供「迁移数据安装」和「卸载后安装」两种方式；两者都保留设置、会话、工作区及用户文件，只替换 ExcelManus 程序。迁移沿用现有数据与快捷方式，重装重新创建快捷方式。

下载由桌面主进程使用系统网络代理完成，不再交给外部浏览器。页面右下角显示真实下载字节数、百分比和平均速度，系统任务栏也同步进度；关闭设置页或重载页面不会丢失主进程中的下载状态。没有可靠总大小时显示不定进度，不虚构百分比。支持取消和失败后重新下载（当前重试从头开始，不支持跨应用重启续传）。

安装包先写入用户数据目录下独立的 `updates/installer-*` 暂存目录，完成后核对发布大小及发布方提供的 SHA-256，再原子改名。启动安装前再次校验本地文件。超时、断流、磁盘空间不足、只读目录、文件损坏和不可信重定向都会停止下载并显示原因，失败尝试的临时文件会清理，不启动安装器。仅接受项目正式发布的匹配架构安装包及 GitHub 资产域名，不关闭 TLS 校验、不使用任意镜像运行程序。

下载成功后自动尝试关闭窗口（保留未保存表格和当前页面运行任务的退出保护），停止随包后台服务，然后交给系统打开已校验安装包并退出桌面进程。如果退出被阻止，保留安装包并显示「退出并更新」供处理完工作后继续；如果安装器启动失败，尝试恢复应用和后台服务，允许重试。Windows 启动 NSIS 安装向导，系统 UAC/安全软件确认仍需用户处理；macOS 打开 DMG 后仍需在 Finder 中将新版替换到原位置，不能视为无人值守自动替换。旧版桌面壳继续提供浏览器下载兜底。

桌面模式禁用源码 Git 更新、应用级备份恢复和远程部署控制。工作簿修订恢复仍属于工作区文件功能。安装新包前，备份 profile 及其之外的已登记工作区。构建、签名和验证见 [Desktop README](../desktop/README.md)。

## 网页更新

网页提供两种更新方式：

- **更新当前源码分支**：「设置 → 版本 → 更新当前源码分支」。先备份 ExcelManus 应用数据，再获取当前分支的新提交、更新依赖并重建网页，服务恢复后核对本次结果并刷新。此操作可能包含尚未正式发布的改动，不代表切换到某个 Release 标签；即使暂无新 Release，受支持的实例也可执行。重装和更新都保留设置、会话，工作区及用户文件不删除、不搬移、不清空。
- **已发布版本提示**：网页独立检查 `/api/app-version` 的构建标识，同时检查后端健康接口中的版本指纹。前端单独部署或后端单独更新均会提示；用户选择刷新后使用新版。同一版的“稍后”不会屏蔽以后的新版本。网页可见时约每 30 秒检查，重新回到页面时立即检查。

刷新前检查未保存、保存失败或冲突中的表格修改，以及当前页面仍在执行的任务；有待处理工作时提示用户先保存或等待，避免自动刷新丢失修改。部署新版的提示本身不会强制刷新。

「检查更新」及启动时的后台检查查询 GitHub 最新正式 Release，不执行 `git fetch`，也不把尚未发布的 tag 当成 Release。API 不可用时尝试官方发布页，每次 HTTP 操作的连接/读取超时为 4 秒。成功结果缓存 5 分钟，失败缓存 30 秒；手动检查跳过缓存，同一安装的并发检查复用正在执行的请求。版本页的本地管理信息独立加载，失败会显示具体原因，不误报“已是最新”。当前源码版本高于最新 Release 时不会提示降级。

一键更新使用请求编号和持久化状态区分“本次成功”“旧结果”和“更新失败但旧服务已恢复”。页面重开时会继续等待该请求。停机期间显示重连等待信息；此时 API 不在线，不显示虚构的实时百分比。只有本次成功且前后端均能响应才自动刷新，失败显示原因并允许返回当前页面。

开始停机前检查 Git、工作分支、未提交修改、目录写权限及网页构建所需的 Node.js/npm，失败时保持服务在线并返回具体原因。服务器即使不允许读取本机备份和安装记录，也会独立加载网页更新能力。兼容没有 `AbortSignal.timeout` 的旧 WebView；普通网页只重连/刷新自身，不能退出浏览器或安装本机 App。Android 客户端连接的网页同样遵循这一边界，本流程不更新 APK。

这是一套网页内更新和重连流程，**更新前后端仍有停机窗口，并非无中断热替换**。首次使用需要先发布包含这些功能的前后端版本。

## 本机 Git 源码

设置页的更新入口调用 `POST /api/v1/version/upgrade`。API 记录请求并启动独立的 `excelmanus.upgrade` 辅助进程，由它完成停机和更新：

1. 根据 `$EXCELMANUS_HOME/runtime.json` 停止启动脚本及相关进程。
2. 将实现覆盖的数据库、配置、`.secret_key` 及 `data/`、`memory/`、`skillpacks/` 等数据备份到 data home 的 `backups/`。网页更新强制执行备份；这不是整个 profile 的完整复制。
3. 获取远端代码并尝试 fast-forward。源码存在未提交修改、分支分叉、用户文件与新版路径冲突时停止更新；不自动 stash，不强制覆盖未跟踪或被 Git 忽略的文件。失败回退代码使用 `reset --keep`，不使用 `reset --hard`。
4. 安装依赖，按需更新并构建前端。
5. 重新执行启动脚本，恢复服务。

获取代码后固定实际成功源的目标提交，避免 origin 失败、GitHub 备用源成功时误合并残留的 origin 分支。依赖安装失败可在官方源与镜像之间双向重试；Windows 会先从 PATH 解析 `npm.cmd`。备份、恢复及停机阶段的异常也进入统一恢复路径，记录本次失败并尝试重新启动服务，旧备份清理失败不阻止更新。

迁移或灾难恢复仍需完整 profile、外部工作区和自定义外部数据库。自动备份不是所有外部目录的镜像；程序更新不会修改这些工作区文件。

也可以停止服务后运行 `./deploy/update.sh`；脚本会拒绝在服务仍运行时直接更新。Windows 使用对应的 `update.ps1` / `update.bat`。

配置保存触发的重启由 `restart.py` 处理，与版本更新是两条流程。源码升级和命令行 `--check` 会比较 Git 提交，不要求包版本号一定增大；网页正式发布检查不拉取分支。更新后应同时核对健康状态、代码版本和实际任务；服务重新响应不一定表示更新成功，例如 fast-forward 失败后可能重新启动原版本。

网页升级要求由 `deploy/start.sh` 或 `deploy/start.ps1` 启动的单工作进程、前后端同机实例，并拒绝在任务执行时开始。备份恢复和远程部署接口继续受本机来源及部署模式限制。不能将 loopback 来源判断视为完整鉴权。

Windows 启动记录使用无 BOM 的 UTF-8 并原子替换；后端同时兼容 PowerShell 5 旧启动记录的 UTF-8 BOM，避免已通过启动脚本运行却被误判为缺少启动记录。

## 服务器

服务器默认禁用网页自身更新。要允许管理员从网页一键更新，需同时满足：

1. 在后端环境设置 `EXCELMANUS_WEB_UPGRADE_ENABLED=1`。
2. 启用已有的登录保护，并通过管理员认证。
3. 通过上述启动脚本运行、单工作进程、前后端同机，且安装目录含 Git 仓库和可用的启动脚本。

`GET /api/v1/version/upgrade/capability` 返回是否可用及原因，设置页会直接展示。此开关只开放版本升级，不开放生产 API 的备份恢复或远程部署执行。多工作进程、分机部署或安装包环境使用各自的发布方式；部署后的网页版本提示仍可用。

运维发布仍可在正确的部署清单下运行：

```bash
bash ./deploy/deploy.sh check
bash ./deploy/deploy.sh --venv .venv
bash ./deploy/deploy.sh history
bash ./deploy/deploy.sh rollback-to --commit COMMIT_SHA
```

脚本支持单机、分机和本地拓扑，更新内容包括代码、依赖、前端产物和服务重启。清单、代理和持久化目录的准备见 [运维手册](ops-manual.md)。

服务器 Git 同步和部分回滚路径会重置部署副本，不能在该目录保留未提交的开发工作。`rollback` 与 `rollback-to` 的行为以各自脚本为准；代码回滚不等于数据库及全部文件回滚。部署历史位于运维机的 `deploy/.deploy_history` 和 `deploy/.deploy_history.json`。

本机 standalone 实例可在配置部署清单后作为运维控制台；服务器网页升级是上文独立、显式启用的入口。

## 数据迁移与恢复

完整恢复需要相匹配的数据库、加密密钥和工作区文件。旧容器卷与旧 `users/{id}/` 目录应由维护者选择后手工迁移，不自动合并多个历史用户库。

首次打开工作区时，系统会尝试把旧 `outputs/backups` 导入 `.excelmanus/revisions/`，迁移标记为 `.excelmanus/migrations/overlay-backups.json`。确需重新执行时使用：

```bash
uv run python -m excelmanus.workspace.migrate /path/to/workspace --force
```

`--force` 表示重新执行迁移；运行前先备份该工作区。Docker 部署入口位于 `deploy/docker-compose.yml`，默认启动两个 API worker、共享持久卷并提供容器健康检查。需要动态代码的强隔离时，再叠加 `docker-compose.isolated.yml` 并配置包含 pandas/openpyxl 的 `EXCELMANUS_DOCKER_IMAGE`；该模式需要 Docker socket，适合受控单租户主机。

## 验证范围

网页更新测试覆盖管理员开关与认证、任务执行中拒绝更新、重复请求互斥、启动失败保持在线、更新结果匹配、重连并发与取消、仅前端部署检测、关闭一次提示后发现下一版，以及刷新前保存检查。临时 Git 仓库测试验证本地修改、未跟踪文件和被忽略的工作簿在冲突时保留原样。未执行真实部署更新。

新增回归测试覆盖下载校验/截断/超时/取消/重复请求、重定向白名单、磁盘和权限错误、安装启动失败恢复、进度订阅及重载恢复、旧 WebView、服务器部分接口拒绝访问、停机前环境检查和备用源目标提交。测试不会启动真实安装器；Windows/macOS 安装、系统代理认证和安全软件拦截仍需在对应系统使用正式打包产物验收。程序无法保证任意网络、权限或第三方安全软件环境都自动更新成功。
