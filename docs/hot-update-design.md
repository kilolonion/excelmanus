# ExcelManus 升级与部署

适用版本：1.8.0 源码 · 更新日期：2026-09-21

[文档导航](README.md) · [运维手册](ops-manual.md) · [English operations guide](ops-manual_en.md)

ExcelManus 当前有桌面应用、本机 Git 源码和服务器三种运行形态。升级会影响正在执行的任务，应在合适的时间进行；当前流程不承诺无中断切换。

## 桌面应用

桌面版从应用资源启动随包前后端及代码运行时，更新方式是安装新的应用包。应用数据保留在 Electron 用户数据目录中的 `profile/`，或显式指定的 `EXCELMANUS_HOME`。

可从「设置 → 版本」或「帮助 → 检查更新」检查正式发布并下载适用的安装包。Windows 检测已有安装后，在原位置提供「迁移数据安装」和「卸载后安装」两种方式；两者都保留设置、会话、工作区及用户文件，只替换 ExcelManus 程序。迁移沿用现有数据与快捷方式，重装重新创建快捷方式。

桌面模式禁用源码 Git 更新、应用级备份恢复和远程部署控制。工作簿修订恢复仍属于工作区文件功能。安装新包前，备份 profile 及其之外的已登记工作区。构建、签名和验证见 [Desktop README](../desktop/README.md)。

## 网页更新

网页提供两种更新方式：

- **一键更新前后端**：「设置 → 版本 → 一键更新前后端」。先备份 ExcelManus 应用数据，再更新代码、依赖并重建网页，服务恢复后核对本次结果并刷新。重装和更新都保留设置、会话，工作区及用户文件不删除、不搬移、不清空。
- **已发布版本提示**：网页独立检查 `/api/app-version` 的构建标识，同时检查后端健康接口中的版本指纹。前端单独部署或后端单独更新均会提示；用户选择刷新后使用新版。同一版的“稍后”不会屏蔽以后的新版本。网页可见时约每 30 秒检查，重新回到页面时立即检查。

刷新前检查未保存、保存失败或冲突中的表格修改，以及当前页面仍在执行的任务；有待处理工作时提示用户先保存或等待，避免自动刷新丢失修改。部署新版的提示本身不会强制刷新。

一键更新使用请求编号和持久化状态区分“本次成功”“旧结果”和“更新失败但旧服务已恢复”。页面重开时会继续等待该请求。停机期间显示重连等待信息；此时 API 不在线，不显示虚构的实时百分比。只有本次成功且前后端均能响应才自动刷新，失败显示原因并允许返回当前页面。

这是一套网页内更新和重连流程，**更新前后端仍有停机窗口，并非无中断热替换**。首次使用需要先发布包含这些功能的前后端版本。

## 本机 Git 源码

设置页的更新入口调用 `POST /api/v1/version/upgrade`。API 记录请求并启动独立的 `excelmanus.upgrade` 辅助进程，由它完成停机和更新：

1. 根据 `$EXCELMANUS_HOME/runtime.json` 停止启动脚本及相关进程。
2. 将实现覆盖的数据库、配置、`.secret_key` 及 `data/`、`memory/`、`skillpacks/` 等数据备份到 data home 的 `backups/`。网页更新强制执行备份；这不是整个 profile 的完整复制。
3. 获取远端代码并尝试 fast-forward。源码存在未提交修改、分支分叉、用户文件与新版路径冲突时停止更新；不自动 stash，不强制覆盖未跟踪或被 Git 忽略的文件。失败回退代码使用 `reset --keep`，不使用 `reset --hard`。
4. 安装依赖，按需更新并构建前端。
5. 重新执行启动脚本，恢复服务。

迁移或灾难恢复仍需完整 profile、外部工作区和自定义外部数据库。自动备份不是所有外部目录的镜像；程序更新不会修改这些工作区文件。

也可以停止服务后运行 `./deploy/update.sh`；脚本会拒绝在服务仍运行时直接更新。Windows 使用对应的 `update.ps1` / `update.bat`。

配置保存触发的重启由 `restart.py` 处理，与版本更新是两条流程。版本检查也会比较 Git 提交，不要求包版本号一定增大。更新后应同时核对健康状态、代码版本和实际任务；服务重新响应不一定表示更新成功，例如 fast-forward 失败后可能重新启动原版本。

网页升级要求由 `deploy/start.sh` 或 `deploy/start.ps1` 启动的单工作进程、前后端同机实例，并拒绝在任务执行时开始。备份恢复和远程部署接口继续受本机来源及部署模式限制。不能将 loopback 来源判断视为完整鉴权。

## 服务器

服务器默认禁用网页自身更新。要允许管理员从网页一键更新，需同时满足：

1. 在后端环境设置 `EXCELMANUS_WEB_UPGRADE_ENABLED=1`。
2. 启用已有的登录保护，并通过管理员认证。
3. 通过上述启动脚本运行、单工作进程、前后端同机，且安装目录含 Git 仓库和可用的启动脚本。

`GET /api/v1/version/upgrade/capability` 返回是否可用及原因，设置页会直接展示。此开关只开放版本升级，不开放生产 API 的备份恢复或远程部署执行。多工作进程、分机部署或安装包环境使用各自的发布方式；部署后的网页版本提示仍可用。

运维发布仍可在正确的部署清单下运行：

```bash
bash ./deploy/deploy.sh check
bash ./deploy/deploy.sh --venv .venv
bash ./deploy/deploy.sh history
bash ./deploy/deploy.sh rollback-to --commit COMMIT_SHA
```

脚本支持单机、分机和本地拓扑，更新内容包括代码、依赖、前端产物和服务重启。清单、代理和持久化目录的准备见 [运维手册](ops-manual.md)。

服务器 Git 同步和部分回滚路径会重置部署副本，不能在该目录保留未提交的开发工作。`rollback` 与 `rollback-to` 的行为以各自脚本为准；代码回滚不等于数据库及全部文件回滚。部署历史位于运维机的 `deploy/.deploy_history` 和 `deploy/.deploy_history.json`。

本机 standalone 实例可在配置部署清单后作为运维控制台；服务器网页升级是上文独立、显式启用的入口。

## 数据迁移与恢复

完整恢复需要相匹配的数据库、加密密钥和工作区文件。旧容器卷与旧 `users/{id}/` 目录应由维护者选择后手工迁移，不自动合并多个历史用户库。

首次打开工作区时，系统会尝试把旧 `outputs/backups` 导入 `.excelmanus/revisions/`，迁移标记为 `.excelmanus/migrations/overlay-backups.json`。确需重新执行时使用：

```bash
uv run python -m excelmanus.workspace.migrate /path/to/workspace --force
```

`--force` 表示重新执行迁移；运行前先备份该工作区。当前不提供 Docker 安装流程、应用内蓝绿切换或多 worker 无中断滚动升级。

## 验证范围

网页更新测试覆盖管理员开关与认证、任务执行中拒绝更新、重复请求互斥、启动失败保持在线、更新结果匹配、重连并发与取消、仅前端部署检测、关闭一次提示后发现下一版，以及刷新前保存检查。临时 Git 仓库测试验证本地修改、未跟踪文件和被忽略的工作簿在冲突时保留原样。未执行真实部署更新。
